ARM D: REQUEST FLOW FOR ONE BUFF

Live buffs pay only for writing and review; name work happens before kickoff

PRECOMPUTE · per event

1. Resolve teams + players on Wikidata
2. Case tables per language
3. Apply press overrides + Tēzaurs
4. Cache, native editor checks once

LIVE · per moment

5. Assemble prompt: style + glossary(sport) + names + 6 examples
6. Generate BuffDraft (structured output)
7. Validators, ms
8. Five reviewers in parallel

DECIDE

9. Orchestrator: dismiss, block or advise
10. Routed repair, max 2 rounds, re-run only affected reviewers
11. Proposal + English gloss + decision log to the operator

The evaluation panel (fresh Claude judge + Gemini) only runs in the lab and in an offline nightly job. It never gates a live buff.

Steps 1 to 4 run once per event at event creation, so the live path pays nothing for Wikidata, Tēzaurs or press lookups.

DATA CONTRACTS · bbl/schemas.py, bbl/reviewers.py

Malformed model output fails loudly instead of reaching an operator

class Finding:
  severity: minor | major | critical

JIL's existing proposal JSON has languages[] with options by id. Buff maps onto one languages[] entry; english_gloss and the decision log would be new optional fields.

DECISION

Native-ear review runs on Claude live. Gemini moves to the offline panel only, where a slow answer costs nothing.

COST NOTE

The first buff per event and language writes ~13k cached prompt tokens (about $0.10). Every later buff reads the cache.

Cost uses $4 / $20 per million input / output tokens, cache writes at 1.25x and reads at 0.05x input. A repair round adds roughly one generate plus the affected reviewers. Lower generation effort or a smaller model was not measured yet.

QUALITY GATES · mapped to the repo’s CLAUDE.md rules

What each PR must prove before merge

100% COVERAGE, NO MOCKS

Validators run against real Hunspell dictionaries and real glossary files. Only the LLM and Wikidata HTTP boundary is stubbed, which the rules allow.

EDGE CASES

Empty options, quiz without an answer, NFC vs NFD text, avoid-term inside the preferred term, foreign letters inside names, hallucinated review spans.

DATA LOSS (RULE 8)

Edit capture: assert the Postgres row exists after the drain, the drain task is in the beat schedule, and a re-delivered message doesn’t double-write.

QUALITY REGRESSION

Nightly golden-set eval (150 buffs per language once natives provide them). A PR that drops approval or raises MQM penalty is flagged, not auto-blocked.

The lab already has 22 offline tests for validators, press overrides and the orchestrator that can be ported as-is.

CI runs without Redis, so the Redis branch of the case-table cache must be covered by unit tests on the cache helpers, as the play-screen section of CLAUDE.md already requires.

SPIKE PROPOSAL: TildeAI/TildeOpen-30b AS A GRAMMAR RANKER

Pick the most grammatical of three drafts with a model built for Baltic grammar

# 1. generate 3 candidate buffs (Claude, temperature varied)
drafts = [generate(moment) for _ in range(3)]

# 2. score each with TildeOpen log-probability
tok = AutoTokenizer.from_pretrained(
  "TildeAI/TildeOpen-30b", use_fast=False)
score = mean_token_logprob(model, tok, d.question)

# 3. keep the best that also passes validators
best = max(passing(drafts), key=score)

WHY

MultiBLiMP grammar test: 99.7% lt, 99.1% lv, 98.3% et, against 95.3 / 91.6 / 92.0% for Gemma 2 27b. Ranking drafts is the same task.

COST

30.7B params, about 61 GB in bf16: one 80 GB GPU, served with vLLM. Scoring needs one forward pass per draft, no generation.

LIMITS

Base model, CC-BY-4.0, no instruction tuning or safety alignment. Ranker only. Success bar: fewer grammar flags on the golden set at equal latency.

Model card: huggingface.co/TildeAI/TildeOpen-30b. The tokenizer must load with use_fast=False. Tilde says a translation model built on it is next, which would be worth re-testing as a writer.
